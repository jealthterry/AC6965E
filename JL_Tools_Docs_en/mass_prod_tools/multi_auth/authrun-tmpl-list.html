Important

Notes:
1. The total size of the authorization executable equals static space + dynamic space:

Static space: SIZE = the total size of the .text +.data +.bss sections
Dynamic space: add the linker flag –plugin-opt=-warn-stack-size=64 in the Code::Blocks build environment; the build then reports the stack usage of each function. For details, see Why Does Linking Warn "stack size limit exceeded"?

When you click Rebuild, the "Build log" window shows the sizes of the data sections

2. Different models have different amounts of RAM. Do not make the algorithm too complex, so that the built executable does not become too large and fail to run during programming;

3. Do not use too large a stack; change buffers defined on the stack to global variables. Otherwise, even if the static space is smaller than the supported executable size, the executable may still hang when it runs during programming;

4. AC701N, JL701N, etc. can be used with or without OTP_CFG_SIZE=512, depending on the SDK design. Newer SDK versions generally support configuring OTP_CFG_SIZE=512, i.e., the flash parameters are written to the otp_cfg area; older SDKs write them to the end of the flash;

4.5.4. Requesting a multi-algorithm authorization patch

If you cannot find the chip model you need, contact Jieli at weiyushu@zh-jieli.com
In the email, state the chip model and the SDK version, and attach the cpu.a of your current SDK:

4.5.4.1. Email request format

To ensure that your request is handled promptly and accurately, send your email in the following format:

Email subject: [Multi-algorithm authorization patch request]-[chip model]-[SDK version] (in Chinese: [申请多算法授权补丁]-[芯片型号]-[sdk版本])
Example: [申请多算法授权补丁]-AC632N-ac63_bt_sdk_release_v2.3.0

4.5.4.2. Notes

  • Make sure the email subject is clear and accurate so that your request can be quickly identified and processed.

  • The cpu.a file in the attachment must be the version for the current chip, to avoid compatibility issues.

  • If you have any questions or need to explain anything further, describe it in detail in the email.

4.5.5. Detailed usage

  1. Download the template project for your chip. (If you cannot find the chip model you need, contact Jieli.)

  2. In the r_makebin.bat script, change Authorization_ID to the agreed ID (234 in the example)

  3. Valid ID range: 64 to 999

Important

Note: when you modify the following two lines in r_makebin.bat, do not add any extra spaces (before or after the equals sign, or at the end of the line); bat scripts are sensitive to spaces.

set Authorization_ID=234

set CHIP_TYPE=AC695X

  1. In the code/main.c file, change the length of the returned encrypted data (i.e., the authorization data)

  2. In the code/main.c file, change how the returned encrypted data (i.e., the authorization data) is generated

    Note

    In the template project, the example XORs the flash uuid and uses the result as the encrypted data. This is a weak method; in general, algorithm companies are advised to replace it with a custom method that others do not know and cannot easily crack

    Note

    1. While programming the chip, the programmer calls the c_main function in the .authrun file

    2. When the programmer calls the callback function c_main, the values flash_id, seq, timestamp and uuid in the ops structure have already been filled in by the programmer

    3. The callback function c_main is responsible for filling out_enc_data and returning out_len

    4. The programmer writes the content of out_enc_data, of length out_len, into the chip

    The programmer's processing flow, in pseudocode, is as follows:

    //---------
struct flash_ops ops;           // This code is implemented on the programmer side; algorithm companies do not need to care about it
ops.flash_id = get_flash_id();  // This code is implemented on the programmer side; algorithm companies do not need to care about it
ops.seq = get_program_seq();    // This code is implemented on the programmer side; algorithm companies do not need to care about it
ops.timestamp = get_timestamp();// This code is implemented on the programmer side; algorithm companies do not need to care about it
ops.uuid = get_flash_uuid();    // This code is implemented on the programmer side; algorithm companies do not need to care about it
ops.out_enc_data = buf;         // This code is implemented on the programmer side; algorithm companies do not need to care about it
ops.len = buf_size;             // This code is implemented on the programmer side; algorithm companies do not need to care about it
//---------
// Note: .uuid is always 16 bytes long


// The algorithm company must implement the c_main function in the .authrun
int out_len = c_main(&ops); // Call the c_main callback function of the .authrun
// After c_main is called, out_enc_data should have been filled and out_len (the length of the encrypted data to write to the chip) returned
// out_len generally cannot exceed 255; for some chip models with fewer resources, the actual limit is smaller. Actual testing prevails

write_to_flash(get_program_address(), // This code is implemented on the programmer side; algorithm companies do not need to care about it
    ops.out_enc_data,                 // This code is implemented on the programmer side; algorithm companies do not need to care about it
    out_len);                         // This code is implemented on the programmer side; algorithm companies do not need to care about it

  3. In Code::Blocks, click Rebuild to generate the .authrun file

  4. Find the corresponding .authrun file in the output directory

  5. Upload the .authrun file to the Jieli server so that it can be sold later

Important

Note:

  1. In general, do not send the .authrun file directly to customers
